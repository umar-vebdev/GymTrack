## 0. Краткий словарь

| Термин | Значение |
|---|---|
| **Модульный монолит** | Одно приложение с одной базой данных, внутри которого код разделён на независимые модули по бизнес-областям. Границы между модулями строгие, как будто это отдельные сервисы. |
| **ООП** | Объектно-ориентированное программирование: код организован в виде объектов, которые хранят данные и поведение вместе. |
| **SOLID** | Пять принципов проектирования классов: S, O, L, I, D (расшифровка в разделе 4). |
| **DTO** | Data Transfer Object: простой объект-контейнер для передачи данных между слоями, без бизнес-логики. |
| **Value Object** | Объект-значение: определяется своим содержимым, а не идентификатором, и не меняется после создания (например, сумма денег). |
| **Репозиторий** | Класс, который скрывает способ хранения данных: остальной код просит «найди абонемент», а не пишет SQL. |
| **Use Case** | Один сценарий приложения («отметить посещение»), оформленный отдельным классом. |
| **Доменное событие** | Сообщение «что-то произошло» (например, «посещение зарегистрировано»), на которое могут реагировать другие модули. |
| **Мультиарендность** | Одна система обслуживает много компаний, а их данные изолированы. |
| **Идемпотентность** | Повторение того же запроса не меняет результат. |
| **Транзакция БД** | Группа операций, которые выполняются все вместе или не выполняются вообще. |

## 1. Цели и границы

### 1.1. Цели

- Единый бэкенд для двух клиентов: веб-кабинета зала (GymTrack-Business) и мобильного приложения (GymTrack-Client).
- Расширяемость: новые функции (каталог, расписание, дневник тренировок) добавляются как новые модули без переписывания старых.
- Тестируемость: бизнес-правила (списание занятия, проверка QR) проверяются быстрыми тестами без базы данных.
- Возможность в будущем вынести любой модуль в отдельный сервис.

### 1.2. Вне рамок

Онлайн-платежи, интеграция с турникетами, микросервисная развёртка с первого дня.

## 3. Архитектура

### 3.1. Общий подход

**Модульный монолит** с разделением каждого модуля на слои. Один репозиторий кода, одна база данных, одно приложение Laravel. Клиенты (веб и мобильное приложение) обращаются к одному REST API.

```
Клиенты:   Веб-кабинет (Business)     Мобильное приложение (Client)
                     \                       /
                      \                     /
                   REST API  /api/v1  (Laravel)
                               |
     ┌──────────┬───────────┬──┴───────┬───────────┬──────────┐
  Identity  Companies   Clients   Memberships   Visits     Sales ...
                               |
                         Shared Kernel
                               |
                  PostgreSQL        Redis
```

### 3.2. Структура проекта

```
app/
  Modules/
    Identity/
    Companies/
    Clients/
    Memberships/
    Visits/
    Sales/
    Billing/
    Notifications/
    Analytics/
    Audit/
    Catalog/            # этап 3
  Shared/               # Shared Kernel
bootstrap/providers.php # регистрация ServiceProvider каждого модуля
tests/
  Architecture/         # тесты на соблюдение границ
```

### 3.3. Структура внутри модуля

```
Memberships/
  Contracts/            # публичные интерфейсы и DTO для других модулей
  Domain/
    Entities/           # бизнес-объекты с поведением
    ValueObjects/
    Enums/
    Events/
    Exceptions/
    Repositories/       # только интерфейсы
  Application/
    UseCases/           # по одному классу на сценарий
    Commands/           # входные DTO
    Queries/            # чтение данных
    Listeners/          # реакции на события других модулей
  Infrastructure/
    Persistence/        # Eloquent-модели, реализации репозиториев
    Migrations/
  Presentation/
    Http/
      Controllers/
      Requests/         # валидация входных данных
      Resources/        # формат ответа
    routes.php
    Policies/           # права доступа

```

### 3.4. Слои и правила зависимостей

| Слой | Ответственность | Может зависеть от |
|---|---|---|
| **Domain** | Бизнес-правила и сущности. Чистый PHP, без Laravel | Только Shared Kernel |
| **Application** | Сценарии использования, оркестрация | Domain, Contracts других модулей |
| **Infrastructure** | БД, внешние сервисы, очереди | Domain, Application |
| **Presentation** | HTTP: контроллеры, валидация, ответы | Application |

Главное правило: **зависимости направлены внутрь, к Domain**. Domain ничего не знает ни о Laravel, ни о базе данных, ни о HTTP.

### 3.5. Взаимодействие между модулями

Модуль **никогда** не обращается напрямую к внутренним классам и таблицам другого модуля. Допустимы только два способа:

1. **Через Contracts.** Модуль публикует интерфейс и DTO в папке `Contracts/`, другие модули зависят только от них.
2. **Через доменные события.** Модуль сообщает «что-то произошло», а заинтересованные модули подписываются.

Запрещено:
- связи Eloquent между моделями разных модулей (`belongsTo` на чужую модель);
- запросы к таблицам другого модуля (JOIN через границу);
- использование чужих классов из Domain или Infrastructure.

Внешние ключи в базе данных на уровне целостности допустимы, но в коде модули ссылаются друг на друга только по идентификаторам.

### 3.7. Допустимые зависимости между модулями

| Модуль | Может использовать Contracts модулей |
|---|---|
| Identity | только Shared |
| Companies | Identity |
| Clients | Identity, Companies |
| Memberships | Companies, Clients |
| Sales | Companies, Clients, Memberships |
| Visits | Companies, Clients, Memberships |
| Billing | Companies |
| Notifications | подписывается на события, остальным не нужен |

| Catalog | Companies, Memberships |

Циклические зависимости **запрещены** (если A зависит от B, то B не может зависеть от A). Если возникла такая потребность, взаимодействие переводится на события.

### 3.8. Подход к доменной модели

Чтобы не усложнять проект сверх меры, выбирается практичный подход:

- **Ядро домена** (Memberships, Visits): богатая доменная модель. Сущности — обычные PHP-классы с поведением и защитой своих инвариантов (правил, которые всегда должны выполняться). Преобразование в таблицы выполняют репозитории.
- **Поддерживающие модули** (Companies, Products, Catalog): допускаются Eloquent-модели напрямую, но вся бизнес-логика всё равно находится в классах Use Case, а не в контроллерах.

## 4. ООП и принципы проектирования

Ниже каждый принцип кратко объяснён и привязан к проекту.

### 4.1. Четыре основы ООП

1. **Инкапсуляция** — объект скрывает внутреннее состояние и меняется только через свои методы. *В проекте:* остаток занятий абонемента — приватное поле, изменяется только методом `consumeVisit()`, который проверяет правила.
2. **Абстракция** — код зависит от интерфейса («что делает»), а не от реализации («как»). *В проекте:* `SmsGateway` — интерфейс, а конкретный SMS-провайдер скрыт за ним.
3. **Наследование** — класс расширяет другой. *Правило проекта:* предпочитать **композицию** (объект содержит другие объекты) наследованию; наследование только для случаев «является» и не глубже двух уровней.
4. **Полиморфизм** — разные реализации одного интерфейса взаимозаменяемы. *В проекте:* разные правила проверки отметки реализуют один интерфейс `CheckInRule`.

### 4.2. Принципы SOLID

**S — Single Responsibility (единственная ответственность).** У класса одна причина для изменения.
*Требование:* один Use Case = один класс = один сценарий. Контроллер только принимает запрос и возвращает ответ, валидация в `FormRequest`, права в `Policy`, логика в Use Case.

**O — Open/Closed (открыт для расширения, закрыт для изменения).** Новое поведение добавляется новым классом, а не правкой старого.
*Требование:* новые правила отметки добавляются новым классом `CheckInRule`, код Use Case не меняется. Новые типы абонементов подключаются новой стратегией списания.

**L — Liskov Substitution (подстановка Лисков).** Реализацию интерфейса можно подставить вместо любой другой без поломки программы.
*Требование:* все реализации `VisitRepository` (Eloquent, in-memory для тестов) ведут себя одинаково по контракту, без неожиданных исключений.

**I — Interface Segregation (разделение интерфейсов).** Много маленьких интерфейсов лучше одного большого.
*Требование:* вместо одного `MembershipService` на 20 методов — узкие контракты: `MembershipLookup` (чтение), `MembershipIssuer` (выдача), и т. д. Каждому потребителю нужен только свой.

**D — Dependency Inversion (инверсия зависимостей).** Верхние слои зависят от абстракций, а не от конкретных классов.
*Требование:* Use Case получает через конструктор интерфейсы. Привязка интерфейса к реализации выполняется в `ServiceProvider` модуля (контейнер Laravel подставляет её автоматически).

### 4.3. Дополнительные принципы

- **DRY** (не повторяйся): одно правило бизнеса живёт в одном месте.
- **KISS** (проще): не вводить абстракцию, пока нет двух реальных реализаций или явной необходимости в тестах.
- **YAGNI** (тебе это не понадобится): не писать код «на будущее» для функций из этапов, которые ещё не начались.
- **Tell, don't ask**: объекту говорят *сделать* (`$membership->freeze()`), а не вытаскивают его данные, чтобы принять решение снаружи.
- **Fail fast**: некорректное состояние приводит к исключению сразу, а не к тихой ошибке дальше.

### 4.4. Применяемые паттерны

| Паттерн | Что это | Где применяется |
|---|---|---|
| **Repository** | Абстракция хранилища | `MembershipRepository`, `VisitRepository` |
| **Strategy** | Взаимозаменяемые алгоритмы | Способ списания (по посещениям, по сроку, безлимит) |
| **Chain of Rules / Specification** | Набор независимых проверок, каждая отвечает за одно условие | Правила отметки посещения |
| **Value Object** | Неизменяемое значение с проверкой | `Money`, `PhoneNumber`, `DateRange`, `QrToken` |
| **State** | Поведение зависит от состояния | Статус абонемента (активен, заморожен, истёк, отменён) |
| **Factory** | Создание сложных объектов | Создание абонемента из типа |
| **Domain Events** | Слабая связь между модулями | `VisitRegistered`, `MembershipIssued`, `PaymentMarked` |
| **Adapter** | Подгонка внешнего сервиса под наш интерфейс | SMS-провайдер, push-провайдер |

## 5. Примеры кода (иллюстрации к принципам)

Это минимальные примеры синтаксиса и структуры, а не готовая реализация.

### 5.1. Value Object (инкапсуляция, неизменяемость)

Суммы хранятся в минимальных единицах (дирамах), чтобы избежать ошибок округления чисел с плавающей точкой.

```php
<?php
declare(strict_types=1);

namespace App\Shared\Domain;

final class Money
{
    private function __construct(
        public readonly int $minorUnits,   // 1 сомони = 100 дирамов
        public readonly string $currency,
    ) {
        if ($minorUnits < 0) {
            throw new \InvalidArgumentException('Сумма не может быть отрицательной');
        }
    }

    public static function of(int $minorUnits, string $currency): self
    {
        return new self($minorUnits, $currency);
    }

    public function add(self $other): self
    {
        if ($this->currency !== $other->currency) {
            throw new \DomainException('Разные валюты');
        }
        return new self($this->minorUnits + $other->minorUnits, $this->currency);
    }
}
```

### 5.2. Сущность с поведением (инкапсуляция, fail fast)

```php
final class Membership
{
    public function consumeVisit(\DateTimeImmutable $at): void
    {
        if (!$this->status->isUsable()) {
            throw new MembershipNotUsable($this->id);
        }
        if ($this->type->isVisitBased()) {
            if ($this->remainingVisits <= 0) {
                throw new NoVisitsLeft($this->id);
            }
            $this->remainingVisits--;
        }
        $this->record(new MembershipConsumed($this->id, $at));
    }
}
```

Состояние (`remainingVisits`) приватно. Снаружи его нельзя изменить в обход правил.

### 5.3. Правила отметки (полиморфизм, Open/Closed)

```php
interface CheckInRule
{
    /** @throws CheckInDenied */
    public function assert(CheckInContext $context): void;
}

final class NotAlreadyCheckedInToday implements CheckInRule
{
    public function __construct(private VisitRepository $visits) {}

    public function assert(CheckInContext $context): void
    {
        if ($this->visits->existsForDay($context->clientId, $context->gymId, $context->date)) {
            throw CheckInDenied::alreadyCheckedIn();
        }
    }
}
```

Остальные правила (`MembershipIsActive`, `NotFrozen`, `WithinAllowedTime`) реализуют тот же интерфейс. Новое правило — новый класс, существующий код не трогаем.

### 5.4. Use Case (SRP, DIP)

```php
final class CheckInClient
{
    /** @param iterable<CheckInRule> $rules */
    public function __construct(
        private QrTokenVerifier $qr,
        private MembershipLookup $memberships,   // Contract модуля Memberships
        private VisitRepository $visits,
        private iterable $rules,
        private EventDispatcher $events,
        private TransactionRunner $tx,
    ) {}

    public function __invoke(CheckInCommand $cmd): CheckInResult
    {
        $gymId = $this->qr->verify($cmd->qrPayload);

        return $this->tx->run(function () use ($cmd, $gymId) {
            $context = new CheckInContext($cmd->clientId, $gymId, $cmd->at);

            foreach ($this->rules as $rule) {
                $rule->assert($context);
            }

            $visit = Visit::register($cmd->clientId, $gymId, $cmd->at);
            $this->visits->save($visit);
            $this->events->dispatch(new VisitRegistered($visit->id()));

            return CheckInResult::from($visit);
        });
    }
}
```

### 5.5. Привязка интерфейсов (DIP)

```php
final class VisitsServiceProvider extends ServiceProvider
{
    public function register(): void
    {
        $this->app->bind(VisitRepository::class, EloquentVisitRepository::class);
        $this->app->bind(QrTokenVerifier::class, HmacQrTokenService::class);
    }

    public function boot(): void
    {
        $this->loadRoutesFrom(__DIR__ . '/Presentation/routes.php');
        $this->loadMigrationsFrom(__DIR__ . '/Infrastructure/Migrations');
    }
}
```

Контейнер подставляет реализацию. В тестах можно привязать `InMemoryVisitRepository`.

### 5.6. Изоляция данных по компании

```php
trait BelongsToCompany
{
    protected static function bootBelongsToCompany(): void
    {
        static::addGlobalScope(new CompanyScope());

        static::creating(function ($model) {
            $model->company_id ??= app(CurrentCompany::class)->id();
        });
    }
}
```

`CompanyScope` автоматически добавляет `WHERE company_id = ?` ко всем запросам Eloquent. Это страховка, но не замена проверкам прав.

## 6. База данных

### 6.1. Общие правила

- Таблицы именуются с префиксом модуля: `memberships_types`, `visits_visits`, `sales_sales`.
- Каждый модуль владеет своими таблицами и миграциями (в `Infrastructure/Migrations`).
- Первичные ключи: автоинкремент `bigint` для внутренних связей и отдельный публичный идентификатор (ULID или UUID) для API, чтобы нельзя было перебирать записи.
- Деньги: целые числа в минимальных единицах + код валюты.
- Время: хранится в UTC, пояс зала используется только при показе и при расчёте «дня».
- Таблицы данных зала содержат `company_id` с индексом.
- Мягкое удаление (`deleted_at`) для сущностей, которые нельзя терять (клиенты, абонементы). Финансовые и аудиторские записи не удаляются.
- Все изменения схемы — только через миграции.

### 6.2. Ограничения целостности

- Уникальное ограничение на посещения: один клиент, один зал, один день — одна отметка (защита от гонок поверх проверки в коде).
- Уникальность номера телефона аккаунта.
- Уникальность `(company_id, client_phone)` в CRM, чтобы не плодить дубликаты внутри зала.
- Проверки (`CHECK`): остаток посещений не отрицательный, сумма не отрицательная.

### 6.3. Индексы

Составные индексы под основные запросы: `(company_id, client_id)`, `(gym_id, visited_at)`, `(client_id, status)` для абонементов, `(company_id, created_at)` для отчётов.

## 7. API

### 7.1. Структура

- Базовый путь `/api/v1`. Версия в пути; ломающие изменения — только в новой версии.
- Группы маршрутов по аудитории:
  - `/api/v1/business/...` — кабинет зала (сотрудники);
  - `/api/v1/client/...` — приложение клиента;
  - `/api/v1/public/...` — каталог без авторизации (этап 3);
  - `/api/v1/platform/...` — админ платформы.
- Маршруты каждого модуля находятся в его `Presentation/routes.php`.

### 7.2. Формат

- JSON; единый формат ответа и ошибок:

```json
{ "data": { } }
```
```json
{ "error": { "code": "ALREADY_CHECKED_IN", "message": "Вы уже отмечены сегодня" } }
```

- Коды ошибок — стабильные строки для клиентов; тексты локализуются.
- Пагинация курсорная или постраничная для всех списков.
- Валидация: только через `FormRequest`; код ответа 422 с перечнем полей.
- Заголовок `Accept-Language` определяет язык сообщений.

### 7.3. Идемпотентность

Операции, которые нельзя выполнить дважды (отметка посещения, создание заявки, отметка оплаты), принимают заголовок `Idempotency-Key`. Повторный запрос с тем же ключом возвращает сохранённый результат первого, а не выполняет действие снова.

### 7.4. Ограничение частоты

Rate limiting на вход, отправку SMS и отметку посещения: лимиты на пользователя и на IP.

## 8. Безопасность

- **Аутентификация:** Sanctum; токены мобильного приложения с возможностью отзыва; cookie-сессия для веб-кабинета.
- **Авторизация (RBAC):** роль сотрудника хранится в связующей таблице «пользователь — компания — роль»; проверка через `Policy` и `Gate`. Каждая Policy проверяет **и роль, и принадлежность объекта компании**.
- **Изоляция тенантов:** глобальный scope + проверка в Policy + автоматические тесты на утечку данных между компаниями.
- **QR:** динамический код (интервал 60 секунд) с подписью HMAC; секрет зала хранится зашифрованно (`Crypt`), код принимается для текущего и предыдущего интервала; сравнение подписи через `hash_equals`.
- **Пароли:** хэширование средствами Laravel (bcrypt или Argon2).
- **Подтверждение телефона:** одноразовый код с ограниченным временем жизни и числом попыток.
- **Входные данные:** строгая валидация; запросы к БД только через параметризованные запросы Eloquent/Query Builder; защита от массового присвоения (`$fillable`).
- **Транспорт:** только HTTPS, заголовки безопасности, настроенный CORS (разрешены только известные домены).
- **Секреты:** только в переменных окружения, не в репозитории.
- **Аудит:** записи о выдаче, отмене, возврате, ручной отметке и изменении ролей сохраняются в неизменяемый журнал (кто, что, когда, откуда).
- **Персональные данные:** согласие хранится с датой; функция удаления/обезличивания аккаунта по запросу.

## 9. Критичные технические сценарии

### 9.1. Отметка посещения (защита от двойного списания)

1. Проверить подпись и срок QR.
2. Открыть транзакцию БД.
3. Заблокировать строку выбранного абонемента (`lockForUpdate`), чтобы два параллельных запроса не списали занятие дважды.
4. Выполнить цепочку правил `CheckInRule`.
5. Списать занятие методом сущности, сохранить посещение.
6. Зафиксировать транзакцию; после неё отправить событие `VisitRegistered`.
7. Уникальный индекс на посещение за день — последняя линия защиты.

### 9.2. Заявка на абонемент

Заявка создаётся со статусом «ожидает оплаты» и сроком жизни 24 часа. Сотрудник ставит отметку об оплате: в одной транзакции фиксируется `PaymentMark`, выдаётся абонемент, заявка закрывается. Просроченные заявки отменяет планировщик.

### 9.3. Связывание клиента и аккаунта

При подтверждении номера телефона событие `PhoneVerified` запускает слушатель модуля Clients: он находит карточки с тем же номером и привязывает аккаунт. Операция идемпотентна.

### 9.4. Фоновые задачи

| Задача | Периодичность |
|---|---|
| Отмена просроченных заявок | каждые 15 минут |
| Завершение истёкших абонементов | ежедневно |
| Напоминания об окончании абонемента (за 7 и 1 день) | ежедневно |
| Контроль пробного периода и подписки зала | ежедневно |
| Отправка SMS и push | очередь, непрерывно |

Все задачи идемпотентны, повторный запуск безопасен. Задачи очереди получают идентификатор компании явно и не полагаются на «текущую компанию» из HTTP-запроса.

## 10. Тестирование

| Тип | Что проверяет | Требование |
|---|---|---|
| **Unit** | Domain: сущности, Value Object, правила; без БД и Laravel | Основной объём тестов, быстрые |
| **Feature** | API-эндпоинты целиком, с тестовой БД | Все сценарии из критериев приёмки бизнес-ТЗ |
| **Архитектурные** | Границы модулей: Domain не использует Laravel, модули не обращаются к чужим внутренним классам, нет циклов | Запускаются в CI, нарушение блокирует слияние |
| **Изоляция тенантов** | Пользователь компании A не получает данные компании B ни одним эндпоинтом | Обязательны для каждого эндпоинта с данными |
| **Конкурентность** | Параллельные отметки не приводят к двойному списанию | Для критичных сценариев |

Покрытие кода: не менее 80% для слоёв Domain и Application. Тестовая БД — тот же тип СУБД, что и в продакшене.

## 11. Качество кода

- `declare(strict_types=1)`, типы параметров и возвращаемых значений у всех методов, `final` по умолчанию для классов, если наследование не задумано.
- Стиль PSR-12 проверяется автоматически (Pint).
- Статический анализ (Larastan) не ниже 8 уровня, без игнорирования ошибок «на потом».
- Границы модулей проверяются Deptrac или архитектурными тестами Pest.
- Классы малы: ориентир до 200 строк; метод до 20 строк; не более 4 аргументов конструктора без веской причины (иначе это признак нарушения SRP).
- Бизнес-логика запрещена в контроллерах, моделях Eloquent (кроме простых геттеров и связей внутри модуля) и миграциях.
- Исключения доменные (`NoVisitsLeft`, `CheckInDenied`), а не общие `Exception`.
- Изменения проходят через code review (или самопроверку по чек-листу, если разработчик один) и CI.

## 12. Наблюдаемость и эксплуатация

- **Логирование:** структурированные логи (JSON) с идентификатором запроса, пользователя и компании; пароли и токены в логи не попадают.
- **Мониторинг ошибок:** отправка исключений в Sentry или аналог.
- **Health-check:** эндпоинт проверки приложения, БД и Redis.
- **Резервные копии:** ежедневный дамп БД, хранение не менее 14 дней, регулярная проверка восстановления.
- **Окружения:** local, staging, production с разными ключами и базами.
- **Развёртывание:** автоматическое, с запуском миграций; откат на предыдущую версию возможен.
- **Конфигурация:** только через переменные окружения.

## 13. Нефункциональные требования (технические)

| Показатель | Требование |
|---|---|
| Отметка посещения | ответ не более 2 с для 95% запросов |

| Часовые пояса | UTC в БД, пояс зала при расчёте «дня» отметки |
| Локализация | сообщения API на русском и таджикском через файлы переводов |

## 15. Критерии готовности (Definition of Done)

Задача считается завершённой, если:

1. Реализован функционал по бизнес-ТЗ и пройдены его критерии приёмки.
2. Код соответствует границам модулей (архитектурные тесты зелёные).
3. Написаны unit-тесты на бизнес-правила и feature-тесты на эндпоинты.
4. Нет ошибок статического анализа и стиля.
5. Эндпоинты описаны в OpenAPI-документации.
6. Миграции обратимы и проверены на тестовых данных.
7. Права доступа и изоляция тенантов покрыты тестами.
8. Изменение прошло CI и проверку (review) перед слиянием.
